# Design decisions

Short records of the choices that shape this project: the context, what was
decided, and what follows from it. Numbers quoted here come from
`python scripts/data_audit.py` on the January to August 2026 export or from
[reports/metrics.md](../reports/metrics.md).

## 1. Data comes from the DLD open data export, one month at a time

**Context.** The brief named two sources. Dubai Pulse (`dubaipulse.gov.ae`) now
answers every URL, including the old `transactions.csv` link, with a permanent
redirect to data.dubai. There, "Real Estate Transactions" is listed as open data,
but its public download is a 7,000-row sample spread across all years; the full
table needs an API key that is granted on request. The DLD open data page offers
a "Download as CSV" button for its transaction search, restricted by its date
picker to the current calendar year.

**Decision.** `dxb-prices download` fetches the same CSV export a visitor gets
from that button, one calendar month per request, three seconds apart. The
endpoint behind the button is undocumented and may change. Requests carry a
User-Agent that names this project and nothing that imitates the DLD page (no
Origin or Referer header). The tool stays inside the current calendar year
because that is all the page offers. The data.dubai sample can be fetched with
`--source dubai-data-sample`, and `python scripts/data_audit.py
--dubai-data-sample` checks that the schema adapter and the cleaning rules read
its Dubai Pulse layout.

**Consequences.** Training data covers January to the last complete month of the
current year. A temporal split needs four complete months (two to train, one to
validate, one to test), so from January to April of each year there is too
little data to retrain; the first retrain of a year runs in May, on two training
months. In January, when no month is complete, `download` says so and exits
normally. The published 2026 snapshot cannot be downloaded again with this tool
after 31 December 2026; its file sizes and SHA-256 checksums identify it. If the
portal changes its request format, the downloader fails with a clear message and
the export can be saved by hand into `data/raw/dld/`.

## 2. No source data in the repository

**Context.** The DLD website terms allow downloading for personal,
non-commercial use and forbid redistribution. The data.dubai Open Data Licence
is broader but asks that adapted data be shared under the same licence and that
no work implies endorsement by the data owner (details in [data.md](data.md)).

**Decision.** Raw exports, cleaned tables, per-community and per-project tables
and trained models are git-ignored. Tests use a synthetic fixture generated by
code. The repository publishes only this project's own evaluation results
(metrics, error analysis, SHAP importance, drift test statistics) and one
illustrative API response in the README.

**Consequences.** Anyone who wants the real results downloads the data
themselves; the report records file sizes and SHA-256 checksums so a run can be
tied to a snapshot. A deployed API does serve derived values from its model
directory: each community's training median price per square metre, and the
number of training sales per community and per project. The retraining workflow
uploads only the metrics report.

## 3. Target: log price per square metre

**Context.** Prices span from about AED 100,000 to over AED 400 million, and the
baseline is expressed per square metre.

**Decision.** The models predict `log(price / size)`; the estimate is
`exp(prediction) * size`. All metrics are computed on the price in dirhams.

**Consequences.** Errors are roughly proportional, which matches the headline
metric (median absolute percentage error). SHAP contributions are additive in
log space, so each factor reads as a percentage effect on price per square
metre. The DLD export has no price-per-metre column; the Dubai Pulse layout
does (`meter_sale_price`), and the schema adapter drops it before anything else
runs, because it is the target divided by a feature.

## 4. Temporal split, selection on validation, one look at the test month

**Decision.** Months are split oldest to newest: training months, then one
validation month, then one test month. A 12-point search over loss function,
tree size and leaf size is scored on the validation month only, with early
stopping on the same month; the community-level model (decision 14) then uses
the chosen settings with its own early stopping. Both models are refitted on
training plus validation months, the baselines are recomputed on the same rows,
and only then is the test month scored.

**Consequences.** The test score is an honest estimate for "next month". The
feature builder, rare-category grouping and lookup tables are fitted on training
rows only; nothing in the features is computed from later months. The validation
month's scores are optimistic by construction, so the reports show them
separately from the test month.

## 5. Fixed validity rules for every row; percentile trimming only inside large communities' training rows

**Context.** Removing unusual prices from the evaluation month would make the
test easier than reality. A first version also trimmed small communities
against the percentiles of the whole training set. That removed entire luxury
communities: every sale in Jumeirah Second (50 sales, median about 101,000 AED
per sqm) lies above the overall 99.5th percentile, so the model and both
baselines never saw it, and its test sales were scored as if the community were
new.

**Decision.** Every split gets the same fixed rules, set wide enough that they
only remove records that cannot be a real apartment sale (size 18 to 3,000 sqm,
price AED 100,000 to 500 million, 2,500 to 250,000 AED per sqm). The branded
penthouses in the data (up to about 184,000 AED per sqm) pass. On top of that,
communities with at least 200 training rows lose the 0.5% and 99.5% tails of
their own price per square metre. Smaller communities are not trimmed. None of
this touches validation or test rows.

**Consequences.** Luxury sales stay in the test month and are visible in the
error analysis by price band, and small luxury communities stay in training.

## 6. Which "sales" count

**Decision.** Keep the Sales group, drop mortgages and gifts. Within sales,
keep sale procedures, including the "Development" variants, and drop lease-to-own
contracts. The "Development" procedures are the non-freehold equivalents of the
ordinary sale procedures (Dubai Investment Park, Silicon Oasis); `python
scripts/data_audit.py` shows the freehold split per procedure.

**Consequences.** Non-freehold communities are covered; the `is_freehold`
feature lets the model separate the two regimes.

## 6a. Filter to sales before looking for repeated transaction numbers

**Context.** A first version dropped every transaction number that appeared on
more than one row, before filtering to sales, and reported all of them as
multi-unit deals. Checking them (`scripts/data_audit.py` lists the groups
involved) showed three different things: portfolio mortgages that really do
cover several units, lease-to-own contracts listed under one number in both the
Sales and Mortgage groups, and 20 sales listed twice with different
nearest-metro labels.

**Decision.** Keep the Sales group first, then keep one row of each sale listed
with different location labels, then drop numbers still on several rows.
Lease-to-own contracts are then removed by the rule that is meant for them.

**Consequences.** The cleaning report names the real reason for each removal,
and the 20 genuine sales are kept once instead of dropped. In the 2026 export
the multi-unit rule then removes nothing; it stays as a guard.

## 7. High-cardinality fields: native categoricals with a minimum count

**Context.** The final training months of the published run hold 121 communities
and 2,172 projects (`reports/metrics.json`, `split`). Target
encoding would need careful out-of-fold handling to avoid leaking each row's own
price.

**Decision.** Use LightGBM's categorical splits with smoothing
(`cat_smooth`, `cat_l2`, `min_data_per_group`). A community, project or nearby
landmark keeps its own level only with enough training rows (30, 40 and 30);
rarer values become `__other__`, missing values `__none__`. Parking (mixes
counts and bay identifiers) and master project (almost always empty) are not
used.

**Consequences.** A project with training sales but fewer than 40 of them is
grouped with the other rare projects in the full model; its own nearest metro,
mall and landmark still reach the model. A project that is not given, or has no
training sales at all, goes to the community-level model (decision 14). The
error analysis shows both cases in the "project given" row, because the test
month is scored the way the API answers (decision 15).

## 8. Community names merged through their Arabic registry names

**Decision.** English names are matched on a case- and punctuation-free key;
Arabic names on a key that unifies letter variants (أ/إ/ا, ى/ي, ة/ه) and strips
diacritics. English spellings that share an Arabic name are one community
("DUBAI MARITIME CITY" and "Madinat Dubai Almelaheyah"). The API accepts either
language.

**Consequences.** This relies on DLD's Arabic names being unique per place. In
the 2026 export no English name maps to two Arabic names; `scripts/data_audit.py`
re-checks this on any new download. The mapping is built from every downloaded
month, not only the training months: it is a lookup of registry names, not
something learned from prices, so it cannot leak a price. A retrain on newer
months can change which English spelling labels a community.

## 9. Per-estimate explanations from LightGBM's own TreeSHAP

**Decision.** The API computes SHAP values with `booster.predict(...,
pred_contrib=True)`, LightGBM's built-in TreeSHAP. The training report uses the
`shap` library for the global summary and records the largest difference
between the two (below 1e-6 in tests).

**Consequences.** The API image does not need `shap` or `numba`. All the
contributions together with the base value add up exactly to the log estimate.
The API returns the five largest as `top_factors` and the combined effect of the
rest as `other_factors_effect_pct`, so the base price per square metre times
all six effects gives the estimate (up to rounding).

## 10. Each model's 80% range comes from its validation residuals

**Decision.** The 10th and 90th percentiles of each model's log residuals on the
validation month define the range around its estimates: the full model's from
the sales whose project it knows, the community-level model's from every sale
scored without its project. The report states how often the test month's real
prices fell inside each range.

**Consequences.** The range has the same relative width for every estimate from
the same model. It is not adjusted for ready units, thin communities or luxury
units, where errors are larger; the model card says so.

## 11. MLflow with a local file store

**Context.** MLflow 3 keeps the file backend in maintenance mode and refuses it
unless `MLFLOW_ALLOW_FILE_STORE=true` is set. It also starts a usage-telemetry
client when it is imported, and Evidently sends usage events unless
`DO_NOT_TRACK` is set.

**Decision.** Use `./mlruns` (a plain directory, as the brief asked) and set the
opt-in inside `dxb_prices.tracking` for `file:` URIs only. Each search trial is
a nested run; the parent run holds the chosen parameters, validation, test and
backtest metrics, the model and the reports. `dxb_prices.telemetry` sets
`MLFLOW_DISABLE_TELEMETRY` and `DO_NOT_TRACK` before either library is imported.

**Consequences.** `MLFLOW_TRACKING_URI=sqlite:///mlflow.db` switches to a
database store without code changes. `mlflow ui` is started by the user, not by
this code, so the README's command sets the same variables.

## 12. Develop and train in the dev container; test on Python 3.12 to 3.14

**Context.** The pipeline needs compiled packages (LightGBM, SHAP with numba,
pyarrow) and the results should not depend on the machine that produced them.

**Decision.** Dependencies are locked with uv (`uv.lock`) for Linux, Windows and
Apple-silicon macOS. The Dockerfile's `dev` target (Python 3.12 on Debian
bookworm) is the reference environment: the published training run and the test
suite ran in it. CI runs the tests on Python 3.12, 3.13 and 3.14 on Ubuntu, and
`requires-python` is `>=3.12`; one lockfile resolves the same package versions
for all three. Optional extras keep the API
image free of MLflow, Evidently and SHAP. Base images come from the AWS ECR
mirror of the Docker Official Images to avoid Docker Hub rate limits.

**Consequences.** Intel macOS is not in the lockfile, because numba has no
current wheels there. Working on the host is possible with `uv sync`, but the
container is what CI and the published numbers match.

## 13. Retraining never deploys

**Decision.** The monthly workflow downloads, checks there are enough final
months, retrains, evaluates and uploads the metrics report. It runs on the 10th
of each month: the downloader treats a month as provisional until seven days
after it ends, because late registrations still arrive, and `check-data` refuses
to test on a provisional month. The workflow has read-only permissions and no
deployment step.

**Consequences.** A person compares the new report with the previous one before
shipping a model. From January to April the scheduled run skips training and
says why (decision 1).

## 14. A community-level model for requests without a known project

**Context.** The first version had one model. When a request left out the
project, the API filled it with the level the model had learned from rare
projects and took the location labels from the community's most common values.
An independent review scored the test month through that path: it was about as
accurate as the community-median baseline, its 80% range was far too narrow,
and the README reported only the path with the project. Leaving the project out
was the default on the Streamlit page and in the README example.

**Decision.** Train a second LightGBM model, the community-level model, on the
same rows and settings but without the project and the nearest metro, mall and
landmark. The API sends a request to the full model when its project has
training sales, and to the community-level model otherwise, and says which one
answered (`model_variant`) with a warning that quotes both models' test error.
The Streamlit page offers the community's projects in a searchable list, fed by
`GET /projects`. Two alternatives were considered: averaging the full model's
predictions over the community's project mix (one prediction per project, and an
explanation that is an average of many), and training the full model with the
project randomly blanked (which changes the model that serves known projects).

**Consequences.** Each answer is a single model's prediction, so its SHAP
factors add up exactly and its 80% range comes from its own residuals. The
model directory holds two boosters (`model.lgb`, `model_community.lgb`).

## 15. Score the test month the way the API answers

**Context.** The first evaluation gave the model DLD's recorded nearest metro,
mall, landmark and freehold flag for every test sale. An API user cannot supply
those, so the published accuracy described a product nobody could use.

**Decision.** `dxb_prices.serving` builds model rows from what a caller supplies
(community, project, size, rooms, off-plan or ready, date) and fills the rest
from the training rows. The API and the evaluation both use it: each test sale
becomes the request a user would send, scored once with its project and once
without. A test pins the two together by sending test sales through the API
and comparing the answers. The score with DLD's recorded labels stays in the
report as a reference.

**Consequences.** The headline is what a user gets. It is a little worse than
the recorded-labels score, and both are published.

## 16. Two baselines and a rolling-origin backtest

**Context.** The brief's baseline, the community median, ignores the building,
while most sales are off-plan units priced from a developer's list. One test
month is also a single draw.

**Decision.** Add a project-median baseline (the project's training median
price per square metre when it has at least five training sales, otherwise the
community's) next to the community median, in the headline and in every
segment table. Add a rolling-origin backtest: every month with at least three
earlier months is scored by models trained only on the months before it, with
default settings and no search, so no setting is chosen with a later month's
data.

**Consequences.** The report shows how much of the gain over the community
median comes from knowing the building, and how much the scores move from
month to month. `dxb-prices train --no-backtest` skips the backtest.
